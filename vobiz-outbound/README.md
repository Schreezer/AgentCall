# Vobiz PSTN relay pilot

This is a separate Cloudflare Worker for Hermes-initiated outbound calls and an inbound answer path that remains disabled at the Worker gate. The purchased DID `+918071580171` is attached to the Vobiz `Hermes_Inbound` Voice Application. Inference-aware Worker version `204271d4-bed8-4c43-827f-2dc92eceb71a` is deployed with inbound admission disabled; DebianBat's inference-aware bridge has inbound admission and direct Hermes Telegram delivery configured and is publicly healthy. A synthetic post-call Sol inference using Hermes credentials succeeded, but a real inbound phone callback, conversation, and Telegram alert remain unproven. Jio forwarding is not configured.

## Routes

| Route | Authentication | Purpose |
| --- | --- | --- |
| `GET /health` | Public | Confirms Worker and D1 are reachable. |
| `POST /v1/pstn-calls` | `Bearer HERMES_PSTN_TOKEN` | Place one call with `Idempotency-Key: <UUID>` and JSON `{ "to": "+91...", "briefing": "...", "opening_speech": "Hi, this is an AI assistant..." }`. `opening_speech` is optional. |
| `GET /v1/pstn-calls/{id}` | `Bearer HERMES_PSTN_TOKEN` | Read status and any available summary. |
| `GET /v1/pstn-calls/{id}/provider-status` | `Bearer HERMES_PSTN_TOKEN` | Read a small Vobiz queued, live, or final CDR state snapshot for an existing local outbound call. No query parameters. |
| `POST /v1/pstn-calls/{id}/reconcile` | `Bearer HERMES_PSTN_TOKEN` | Mark an abandoned outbound row failed only after Vobiz confirms a final CDR. Idempotent; no body or query parameters. |
| `GET /v1/inbound-calls` | `Bearer HERMES_PSTN_TOKEN` | Read the 20 most recent inbound calls and bounded summaries, newest first. No full transcript or detailed `inbound_report` is included. |
| `GET /v1/inbound-calls/{id}` | `Bearer HERMES_PSTN_TOKEN` | Read one inbound call, including a bounded, code-redacted `inbound_report` if the bridge supplied one. |
| `POST /v1/vobiz/{answer,ring,hangup}/{id}/{token}` | Per-call 256-bit callback token, plus Vobiz V2/V3 HMAC when present | Answer XML and provider call state. |
| `POST /v1/vobiz/inbound/answer` | Required Vobiz V2/V3 HMAC | Receive `Event=StartApp` from the Voice Application Answer URL. |
| `POST /v1/vobiz/inbound/hangup` | Required Vobiz V2/V3 HMAC | Receive `Event=Hangup` from the Voice Application Hangup URL. |
| `POST /v1/vobiz/inbound/answer/{token}` | Canonical 43-character `VOBIZ_INBOUND_CALLBACK_TOKEN`; valid Vobiz HMAC also required when signature headers are present | Receive an unsigned-provider `Event=StartApp` callback without weakening the fixed HMAC-only route. |
| `POST /v1/vobiz/inbound/hangup/{token}` | Canonical 43-character `VOBIZ_INBOUND_CALLBACK_TOKEN`; valid Vobiz HMAC also required when signature headers are present | Receive an unsigned-provider `Event=Hangup` callback without weakening the fixed HMAC-only route. |
| `GET /v1/vobiz/bridge/calls/{id}` | `Bearer VOBIZ_BRIDGE_RELAY_TOKEN` | Give the media bridge its bounded call brief and Vobiz call UUID. |
| `POST /v1/vobiz/bridge/calls/{id}/claim` | `Bearer VOBIZ_BRIDGE_RELAY_TOKEN` | Atomically claim the call once before opening a Codex session. |
| `POST /v1/vobiz/bridge/calls/{id}/events` | `Bearer VOBIZ_BRIDGE_RELAY_TOKEN` | Report connected, ended, or failed; optionally include summary or bounded transcript. |
| `POST /v1/vobiz/bridge/notifications/claim` | `Bearer VOBIZ_BRIDGE_RELAY_TOKEN` | Claim one due owner alert from the durable outbox. Returns `{ "notification": null }` when none is due. |
| `POST /v1/vobiz/bridge/notifications/{call-id}/ack` | `Bearer VOBIZ_BRIDGE_RELAY_TOKEN` | Mark an alert sent after Hermes Telegram or the paired Caller relay accepted it. Repeated acknowledgements are safe. |
| `POST /v1/vobiz/bridge/notifications/{call-id}/reject` | `Bearer VOBIZ_BRIDGE_RELAY_TOKEN` | Quarantine a claimed alert after a permanent delivery failure. JSON `reason` is only `invalid_claim`, `caller_relay_rejected`, or `caller_relay_conflict`. Repeated rejection is safe. |

The Worker accepts canonical Indian `+91` destinations on the `VOBIZ_ALLOWED_DESTINATIONS` allowlist only. It checks the Codex bridge's `/health` for `codex_ready: true`, inserts a call record, and asks the bridge to prepare that call's Codex realtime session **before** sending the Vobiz dial request. Preparation is a signed, action-scoped `GET /caller-vobiz/prepare/{id}` request derived from the configured bridge WSS origin and path. It must return HTTP 200 with `{ "ok": true, "prepared": true }` within 40 seconds; otherwise the Worker records `codex_prepare_failed`, requests best-effort cleanup, and does not dial. Hermes's 65-second call-create timeout covers this bound plus the 10-second provider request. The Worker enforces a rolling 1000 ms gap before provider dispatch and three attempts per minute, and permits only one active call at a time. It sets a 3-minute after-answer call cap and currently leaves the unanswered ring duration to Vobiz. It does not use an OpenAI API key or an alternate voice provider. Vobiz callback comparison accepts exact Indian 10-digit national numbers as well as `+91` numbers. A `queued` response means Vobiz accepted the request, not that the recipient answered. `dispatch_unknown` means the provider may have accepted a request that timed out; never redial that idempotency key automatically.

The bridge preparation token uses HMAC-SHA256 over a base64url JSON payload containing only `{ "v": 2, "id": "<call UUID>", "exp": <Unix seconds>, "direction": "outbound", "action": "prepare" }`. A separate `action: "cancel"` token requests cleanup after a definite preparation, rate-limit, or provider failure, or after a Hangup before the bridge claimed the call. Both calls use `Authorization: Bearer` with manual redirect handling so the credential cannot be forwarded to another origin. A provider timeout, 5xx, or missing request UUID keeps the prepared session available for a late callback until the bridge's 180-second TTL. Idempotency retries return the existing call state and never prepare or dial again. Structured `vobiz_prewarm_ready`, `vobiz_prewarm_failed`, and `vobiz_provider_dispatch` logs record call ID, bounded elapsed milliseconds, outcome or failure code; they omit the token, destination, and brief. The phone audio stream still begins only after Vobiz answers; prewarming moves Codex setup ahead of ringing.

During preparation, D1 stores `provider_status=preparing_voice`. A status read or another create request marks that row `failed`/`prepare_interrupted` if it remains there for 60 seconds and requests best-effort bridge cancellation, freeing capacity for a new call. Immediately before sending the Vobiz request, the Worker must atomically change it to `provider_dispatch_started`; an older suspended request cannot dial after the stale cleanup wins or after its own 60-second age limit. A row stranded after `provider_dispatch_started` has an uncertain provider outcome and is not redialed automatically. The outbound Answer callback validates the provider identity and live D1 row, then returns a signed stream without a second bridge health request. The bridge requires the matching prepared, live session when that stream starts. New outbound calls and inbound answer admission continue to require `codex_ready:true`.

The optional opening speech is limited to 320 characters, strips extra horizontal or line whitespace, rejects control characters, and must explicitly say `AI` or `artificial intelligence`. Its normalized text is part of the idempotency hash and is passed to the bridge as `opening_speech`. Without it, the Worker uses a generic AI-disclosed greeting.

The provider-status diagnostic maps a Worker call ID to its stored Vobiz UUID. It tries Vobiz's [queued call](https://www.vobiz.ai/docs/call/retrieve-queued-call), [live call](https://www.vobiz.ai/docs/call/retrieve-live-call), then [single CDR](https://www.vobiz.ai/docs/cdr) GET endpoints, each with a 2.5-second deadline. A `404` at one stage leads to the next; three `404`s return `provider_record_not_found`. It only returns `source`, normalized `state`, and, for a CDR, bounded `hangup_cause`, `hangup_cause_code`, and `failure_code`; nonnegative integer `ring_time_seconds`, `duration`, and `billsec` up to one day when valid; an `answer_time_present` boolean; recognized `hangup_source` and `hangup_disposition`; and validated `codec`, MOS (1–5), jitter in milliseconds, and packet loss percent. Invalid or missing quality metrics are omitted. Zero `ring_time_seconds` is not evidence of ringing. A CDR with `answer_time_present:false` and `billsec:0` does not prove the recipient answered, regardless of a `NORMAL_CLEARING` cause. Vobiz warns that `hangup_source` is unreliable for conference legs, so it is diagnostic context rather than proof of who ended a conversation. The route does not return phone numbers, caller name, raw timestamps, provider response bodies, credentials, or arbitrary failure text. This is a read-only snapshot: it does not place, retry, cancel, or update a call. If the outbound dispatch never yielded a Vobiz UUID, it returns `provider_call_id_unavailable` instead of guessing or retrying. This route is intended for owner diagnosis, not high-frequency polling.

The reconcile route uses that provider probe to resolve a local outbound call stranded by missing or rejected callbacks. It sets `failed`, `provider_ended_without_callback`, and `ended_at` only when Vobiz returns a final CDR and the row is still `dispatching`, `queued`, `ringing`, or `dispatch_unknown`, with no end time or bridge claim. The database update repeats every condition atomically, including the stored Vobiz UUID, so a callback or bridge claim that arrives during the provider request wins. It returns the current public call status after the update; repeat requests return the same terminal status without another provider lookup. A queued or live provider result returns HTTP 409 with the current call and no mutation. Provider lookup errors also leave the row unchanged. This route never places, cancels, or retries a provider call and never changes a connected, completed, failed, canceled, or bridge-claimed row.

Vobiz's [Make Call API](https://www.vobiz.ai/docs/call/make-call) documents `answer_url`, `ring_url`, `hangup_url`, and `time_limit`. It defines `hangup_on_ring` from the start of ringing, so the Worker omits it: the September 30 test call ended roughly 30 seconds after dialing despite being answered. The API example shows `ring_timeout`, but its behavior is not defined in the parameter table or OpenAPI schema, so the Worker omits that field as well. Its [callback validation guide](https://www.vobiz.ai/docs/concepts/validating-callbacks) says HMAC headers may be absent unless callback URL credentials are configured. Every URL therefore also carries a unique random token whose hash is stored in D1. When V2/V3 signature headers are present, the Worker validates them and rejects invalid ones. It requires the stored Vobiz `CallUUID` and compares caller ID and destination when Vobiz supplies them.

Automatic Cloudflare observability logs and traces are disabled for the pilot because callback URLs contain per-call tokens. Nonce records store only a hash of the callback path. Application error logging omits the request URL and bridge failure details.

Ring and Hangup callbacks return HTTP 200 as [Vobiz requires](https://www.vobiz.ai/docs/concepts/callbacks). Hangup uses documented `CallStatus` and `HangupCause`, plus whether the call reached the answer or bridge stage. The outbound Answer callback returns the prepared stream without fetching bridge health again; if the prepared session is absent, the bridge closes the stream. A normal provider Hangup alone is not proof of voice: the Worker records `completed` only after an authenticated bridge `ended` report. Until then it fails closed, including when the stream was claimed; a delayed `ended` report can complete a normally ended provider call. Provider or bridge failure remains failed across duplicate callbacks. Migration `0006_outbound_terminal_event.sql` stores the independent provider and bridge outcomes and must be applied before deploying this Worker version. The bridge persists the first terminal `ended` or `failed` report on DebianBat and replays it until this Worker accepts it, including after a bridge restart. Turning `VOBIZ_OUTBOUND_ENABLED` off blocks new calls while existing callbacks and bridge status reports continue.

## Inbound staging

The fixed inbound Answer and Hangup routes require a valid Vobiz V2 or V3 HMAC signature and 20-digit nonce. Because Vobiz documents that signature headers can be absent when callback URL credentials are not configured, the Worker also offers token-suffixed Answer and Hangup routes. Both token routes require one canonical 43-character, 256-bit bearer stored as `VOBIZ_INBOUND_CALLBACK_TOKEN`. Keep that token confidential: it is part of the callback URL and must never appear in source, logs, screenshots, or documentation. A request that supplies Vobiz signature headers must still pass HMAC validation; the bearer cannot override an invalid signature.

Both authentication paths validate `auth_id`, `Direction=inbound`, `CallUUID`, `Event`, and `To` matching the owned `VOBIZ_NUMBER`. The token path binds the first exact path and form body for each callback kind and `CallUUID` into the existing D1 nonce table, so an altered retry is rejected. The fixed HMAC path retains signed nonces because Vobiz signs the URL and nonce rather than the form body. See [Vobiz callback validation](https://www.vobiz.ai/docs/concepts/validating-callbacks) and [callback events](https://www.vobiz.ai/docs/concepts/callbacks).

With `VOBIZ_INBOUND_ENABLED=false`, an authenticated Answer returns HTTP 200 with `<Hangup/>`; Hangup returns HTTP 200. The Worker records one minimal `blocked_disabled` row per Vobiz `CallUUID` with no caller number, report, bridge token, or Codex session. This lets an owner check whether Vobiz actually reaches the configured callback path before any AI answers a real call. Read it through the authenticated inbound list/status routes. The public `/health` confirms Worker and D1 only; it does not mean the inbound agent is enabled.

With `VOBIZ_INBOUND_ENABLED=true`, Answer checks the bridge's `/health` within 1.2 seconds and requires both `codex_ready:true` and `inbound_enabled:true`. Only then does it create one inbound record and return a bidirectional `<Stream>` to the bridge, with a short-lived, signed, direction-scoped token. The bridge must match `start.callId` to the stored Vobiz UUID and atomically claim the call; repeated Answer callbacks do not create a second record or second claim. This personal pilot allows one active call across inbound and outbound routes. A second inbound caller receives `<Hangup/>` and a `failed`/`another_call_active` record; a concurrent outbound request gets HTTP 409. If the bridge is unavailable, the Worker records `failed` and returns `<Hangup/>`. `From` may be absent, withheld, foreign, or spoofed. `caller_number` is unverified metadata, and `source_type` remains `unknown`; this path cannot tell whether the caller dialed the DID or reached it by carrier forwarding.

The bridge uses a fixed inbound message-taking policy and an AI-disclosed greeting. The Worker stores only a bounded report and summary from the bridge, not the full transcript. Before storage, it removes controls and bidirectional formatting and redacts code and phone-like digit sequences, including separated and non-ASCII digits. The deployed bridge can submit only redacted caller turns to a fresh, restricted `gpt-6-sol` thread after the call and spend at most 20 seconds producing a reason. A validated result is explicitly labeled `Likely reason (inferred, unverified):`; it remains an inference rather than a verified account. A synthetic inference through Hermes credentials produced a grounded labeled result. The same path has not yet been proven from a real inbound phone call.

`completed` means the phone/media lifecycle ended after the bridge connected; it does not prove a caller left a message or acknowledged anything. Public status fields `delivery_status` and `acknowledgement_status` therefore remain `unknown` unless supported by separate evidence. A Hangup before bridge media connects is recorded as `failed`.

A completed inbound bridge event also inserts one durable, idempotent outbox item. The deployed Worker preserves the exact `Likely reason (inferred, unverified):` label when the saved report contains a validated Sol result. Otherwise, a quoted report becomes `Caller said (unverified):`; if there is no captured caller message, the Worker stores the existing generic alert. Every alert is at most 180 Unicode characters. The Worker removes controls, bidirectional formatting, and digits, and never reads the caller number, Hermes context, or a full transcript to build it. The bridge durably stores the attributed quote before attempting inference, so a timeout, model error, cancellation, or process restart retains quote-first fallback evidence. The first terminal event accepted by the Worker freezes the saved report and alert; later event retries cannot change them.

The bridge can send that stored alert directly to one explicit Telegram chat through DebianBat's existing `hermes send` command. This mode requires both `HERMES_SEND_EXECUTABLE` and `HERMES_NOTIFICATION_TARGET`; it reuses Hermes's existing Telegram credentials and does not start another poller or gateway. The bridge acknowledges the outbox only after `hermes send` returns structured success. A mode-0700 directory of mode-0600 delivery receipts prevents most duplicates if the Worker acknowledgement must be retried. A process crash after Telegram accepts a message but before the receipt is durably written can still duplicate it.

If Hermes notification mode is unset, the paired Caller relay remains the fallback and uses `vobiz-inbound-{call-id}` as its idempotency key. A crash after Caller accepts the request but before Worker acknowledgement may resend it, but the stable key and unchanged message let Caller return the existing call instead of scheduling a duplicate. Transient delivery failure remains `pending` and becomes due again after 30 seconds. For an invalid claim or permanent Caller relay 400/409/422 response, the bridge can reject the claimed alert with a fixed reason code; the Worker quarantines it so later alerts can proceed. A quarantined alert is retained for investigation and is not retried automatically. `owner_notification_status` on authenticated inbound list/detail responses is `pending`, `sent`, `failed`, or `null`; `failed` means quarantined. `sent` means the configured delivery command or relay accepted the alert, not that the owner read it or the iPhone displayed it. Without either complete delivery configuration, the bridge does not claim items and they remain pending.

This pilot has no automatic record deletion. Inbound caller metadata and bounded reports remain in D1 until deliberately removed; signed nonce hashes and token-route callback fingerprints are retained to prevent replay or altered retries. Decide a retention and export policy before sustained use.

The DID is already attached to the Vobiz `Hermes_Inbound` Application, which immediately controls direct calls to `+918071580171`. The token-capable Worker is deployed with inbound off, a fresh callback bearer is stored as a Cloudflare secret, and the Application's distinct POST Answer and Hangup URLs use the token-suffixed routes. DebianBat's Codex bridge and Hermes Telegram delivery are configured and public health reports ready. The remaining activation sequence is: confirm one real `blocked_disabled` Answer/Hangup callback; then enable the Worker flag and place a controlled direct-DID conversation test. Do not enable Jio forwarding until that full call and owner message are proven. [Attaching a number](https://www.vobiz.ai/docs/applications/attach-number) changes incoming routing immediately.

## Configuration

Dedicated D1: `caller-vobiz-outbound` (`6a478995-5ebf-4d77-a7e5-3a7d700e4a91`, APAC). Run `npm run check`, then apply all pending migrations, including `0005_notification_quarantine.sql`, to that database before deploying. Keep all required values in Wrangler secrets, not source:

| Secret | Value |
| --- | --- |
| `HERMES_PSTN_TOKEN` | Separate random bearer shared with Hermes as `HERMES_PSTN_TOKEN`. |
| `VOBIZ_BRIDGE_RELAY_TOKEN` | Separate random bearer shared with the bridge as `VOBIZ_RELAY_TOKEN`. |
| `VOBIZ_BRIDGE_SECRET` | Random HMAC key shared with the bridge for short-lived WebSocket tokens. |
| `VOBIZ_AUTH_ID`, `VOBIZ_AUTH_TOKEN` | Vobiz account credentials from its console. |
| `VOBIZ_INBOUND_CALLBACK_TOKEN` | Optional canonical 43-character base64url encoding of 32 random bytes for token-suffixed inbound Answer and Hangup URLs. Treat the full callback URLs as bearer credentials. |
| `VOBIZ_NUMBER` | Owned Vobiz caller ID in E.164 form. |
| `VOBIZ_PUBLIC_BASE_URL` | Exact deployed Worker HTTPS origin, with no path or trailing query. |
| `VOBIZ_BRIDGE_WSS_URL` | Public WSS bridge endpoint including its `/vobiz` path. |
| `VOBIZ_ALLOWED_DESTINATIONS` | Comma-separated canonical `+91` numbers permitted for outbound calls. For the pilot, set only the user's own self-test number. |
| `VOBIZ_OUTBOUND_ENABLED` | Set to `false` first. Set to `true` only for the controlled outbound pilot. |
| `VOBIZ_INBOUND_ENABLED` | Public Wrangler var pinned to `false`. Change to `true` only after authenticated callback proof, healthy inbound bridge, and a controlled DID routing test. |

The bridge should set `VOBIZ_RELAY_URL` to this Worker's public origin. Hermes should set `HERMES_PSTN_RELAY_URL` to the same origin. Their bearer tokens are distinct. No inbound number linkage is needed for outbound calls.

Inbound WebSocket streams keep the short-lived V1 token containing the Worker call ID, direction, and expiry. The bridge fetches their context, compares Vobiz `start.callId` with the authenticated provider call ID, and claims the call before starting Codex. Prepared outbound streams use a separate signed V2 token with the callback-verified provider UUID. The bridge requires an already prepared Codex session for that Worker call ID and checks the Vobiz start ID before it attaches audio. Its remote claim and connected report run in the background so a transient bridge-to-Worker HTTPS delay cannot hold the greeting; a terminal outbound report can still be stored after provider Hangup. Missing preparation or invalid identity fails closed. Neither token carries the call brief or account secrets in the stream URL. V2 prepare and cancel action tokens have a distinct schema and are never accepted as stream tokens.

The bridge stores terminal events in a private local spool before posting them here. The first saved outcome wins; failed posts are retried in the background after network recovery or process restart. The local record contains a fixed outbound failure code or at most 500 characters of redacted recipient speech, never audio, the full transcript, or credentials. A full or unavailable spool prevents outbound preparation, so it cannot silently dial a call whose result cannot be saved. Spool replay confirms Worker acceptance, not handset audibility or call quality.

## Local validation

`npm run check` runs generated binding checks, TypeScript, Worker tests, and a dry-run bundle. The test runner overrides its compatibility date to match the latest `@cloudflare/vitest-pool-workers` runtime while production uses the current compatibility date from `wrangler.jsonc`.
