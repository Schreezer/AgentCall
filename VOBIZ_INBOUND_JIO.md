## Intended path

1. A caller dials the owned Vobiz number directly, or Jio conditionally forwards a busy cellular call to it after the direct DID path is proven.
2. A dedicated Vobiz voice Application posts its **answer** and **hangup** callbacks to the isolated `vobiz-outbound` Worker. The Worker authenticates the callback, checks the owned destination and bridge readiness, records the call, and returns VobizXML for a bidirectional audio stream.
3. The separate DebianBat Vobiz bridge joins that stream to Codex App Server using Hermes's `openai-codex` credential pool and the owner's ChatGPT/Codex authentication tokens. GPT Live handles speech; its substantive text handoffs use the pinned `gpt-6-sol` thread. Sol is the text reasoning model, not the voice model. A short greeting or acknowledgement may be generated by GPT Live without a Sol handoff. The first two-way carrier conversation is verified, but a substantive Sol handoff is still unproven. There is no OpenAI API key or alternate voice provider in this path. See [bridge design](integrations/hermes/urgent-caller/VOBIZ_CODEX_BRIDGE.md).
4. The agent identifies itself as an AI assistant, asks why the person called, and takes a bounded message. It does not expose private Hermes context or use Hermes tools for an unknown caller. After the call, Caller's existing **standard notification** path can show a short, digit-redacted excerpt labeled as unverified caller speech, with a generic fallback when no reason was captured. Verify that notification separately; an ended audio stream alone does not prove a useful message was taken or that the owner saw a notification.

Vobiz documents voice [Applications](https://www.vobiz.ai/docs/applications/create-application), [number attachment](https://www.vobiz.ai/docs/applications/attach-number), and [bidirectional streams](https://www.vobiz.ai/docs/concepts/streaming-websockets). Attaching the number immediately sends **all calls to that DID** to the new Application. Create a dedicated Application with explicit, distinct `answer_url` and `hangup_url` values from the deployed inbound Worker; Vobiz otherwise defaults `hangup_url` to `answer_url`. Leave `default_number_app` and `default_endpoint_app` false. Save the DID's previous Application binding so it can be restored.

## Limits of the iPhone and Jio path

[Jio offers](https://www.jio.com/help/faq/mobile/services/hd-voice/what-are-different-types-of-call-forwarding/) unconditional, no-answer, busy, and not-reachable forwarding. It does **not** list “unknown caller only” forwarding. The initial Jio policy for this personal route is **Busy only**, covering every caller who meets that carrier condition. Confirm actual behavior on this SIM because [call waiting](https://www.jio.com/help/faq/mobile/services/hd-voice/what-call-management-services-are-offered-by-jio/) may present a second call while the line is in use. [Apple describes Decline](https://support.apple.com/en-in/guide/iphone/iph3c9947bf/ios) as sending a call to voicemail or disconnecting it in some regions; neither Apple nor Jio documents Decline as a guaranteed Busy-forwarding trigger. Do not claim that tapping Decline hands one call to GPT Live until a controlled Jio test proves it.

The Caller iPhone app's PushKit/CallKit UI handles **its own VoIP calls**; it does not capture or answer a Jio cellular call. Apple's [CallKit](https://developer.apple.com/documentation/callkit?changes=_2) and [Call Directory](https://developer.apple.com/documentation/callkit/identifying-and-blocking-calls?changes=l_10_8_7&language=objc) interfaces cover app VoIP calls and caller identification/blocking. For this feature, the server-side agent answers the Vobiz leg and the app receives a post-call notification. Carrier forwarding covers Jio voice calls, not personal WhatsApp calls.

## Enable in two stages

### Stage 1: Direct DID calls only

- Confirm that the purchased DID is owned, accepts ordinary incoming voice calls, and is an eligible **10-digit Indian mobile or landline** destination for Jio. [Jio's activation FAQ](https://www.jio.com/help/faq/mobile/services/hd-voice/how-can-i-activate-call-forwarding-service/) excludes international, BSNL, and the subscriber's own Jio number. Check number type and any forwarding charges or restrictions with the providers before using the personal line.
- Migrations `0002_inbound.sql`, `0003_caller_notification_outbox.sql`, `0004_notification_message.sql`, and `0005_notification_quarantine.sql` are applied, and the isolated Worker's inbound routes are deployed with inbound **disabled**. Before DID attachment, provision callback URL credentials and require Vobiz V2/V3 HMAC authentication. [Vobiz's callback guide](https://www.vobiz.ai/docs/concepts/validating-callbacks) says signature headers may be absent unless those credentials are configured. Reject missing/invalid signatures, replays, wrong account, wrong DID, and duplicate call IDs. Keep credentials in secrets, never in this file or callback URLs. Confirm the exact inbound route names against the deployed [`vobiz-outbound` README](vobiz-outbound/README.md).
- DebianBat's standalone bridge service and public route are installed and public health returned HTTP 200 after recovery, but WAN RTT and loss remain degraded. Recheck sustained reachability and Codex readiness before enabling inbound. Then verify an authenticated Vobiz WSS stream, actual GPT Live audio, a `gpt-6-sol` text handoff, and the bridge's one-call capacity. Follow [bridge deployment notes](integrations/hermes/urgent-caller/VOBIZ_CODEX_BRIDGE.md) and the Hermes host runbook. Do not start a second Hermes Telegram poller or restart its gateway to enable this standalone bridge.
- Configure a dedicated Vobiz Application using the canonical [Create Application API](https://www.vobiz.ai/docs/applications/create-application) with `answer_method=POST`, `hangup_method=POST`, explicit answer/hangup URLs, and a tested safe fallback for an unavailable answer endpoint if supported. After synthetic callback/security tests and a healthy bridge, [attach the DID](https://www.vobiz.ai/docs/applications/attach-number) **in a controlled test window while inbound admission is still disabled**. Attachment is an immediate live routing change. Call the DID directly to observe a real Answer and Hangup callback; verify their HMAC signatures and replay handling without logging secrets. This first call may fail closed. If either callback is unsigned, leave inbound disabled, restore the prior DID binding, and resolve the Vobiz callback configuration with Vobiz support. Only after real callback proof should inbound admission be enabled and a second direct DID call made for audio validation.
- From another phone/network, call the DID **directly**. Confirm the AI disclosure, intelligible two-way speech, a substantive Sol handoff, clean hangup, correct call record and bounded message/result, and a short unverified caller-reason alert on the owner's iPhone. Test a caller who gives no reason and one who speaks in the expected non-English language; check redaction, fallback, and whether the iPhone actually displays the alert. Test no answer/bridge unavailable, occupied bridge, invalid webhook signatures, and duplicate callbacks. The call record and notification must distinguish `unknown` delivery/acknowledgement from evidence that a message was actually delivered and acknowledged. Retest after relevant Codex or bridge upgrades.

### Stage 2: Jio Busy, only after Stage 1 passes

- With the owner at the Jio SIM and able to test and roll back, use [MyJio's documented flow](https://www.jio.com/help/faq/mobile/services/hd-voice/how-can-i-activate-call-forwarding-service/): Profile → Mobile Settings → Service Settings → Call Forwarding → Voice → choose **Busy**, complete SIM verification, and enter the Vobiz DID as a 10-digit number. Jio says the iPhone settings surface supports unconditional forwarding only, so do not use it for this conditional policy.
- Place controlled calls to the personal Jio line from a separate number. Verify a normally answered call still reaches the owner. Separately test a call while the Jio line is already in use and a call that the owner explicitly declines; record the outcomes with call waiting on and off if the first run is ambiguous. A declined call may go to voicemail or disconnect instead of forwarding. Check the agent's greeting, recorded reason, Caller notification, and actual Jio/Vobiz call records. Do not treat a Worker `200`, APNs acceptance, or a Vobiz `completed` status alone as end-to-end proof.
- If Decline does not forward, discuss **No Answer** as a separate later policy: letting a call ring out would apply to every unanswered caller. Keep a note of the active condition and previous DID binding so rollback is immediate. Do not enable unconditional forwarding merely to make a test pass.

## Rollback

1. First disable the active **Busy** forwarding in [MyJio](https://www.jio.com/help/faq/mobile/services/hd-voice/how-can-i-deactivate-call-forwarding-service/) after SIM verification; Jio also documents per-condition deactivation short codes on that page. Test from another number that calls no longer divert.
2. If direct DID routing is failing, restore the recorded previous Vobiz Application binding. If there was no prior binding, [detach the DID](https://www.vobiz.ai/docs/applications/detach-number); Vobiz says detachment leaves the number owned but stops routing it to that Application. Test direct DID behavior after the change.
3. Disable new inbound admission in the isolated Worker. Let active calls finish or end them deliberately before stopping the standalone bridge. Preserve call records for diagnosis; do not alter Hermes's gateway lifecycle for this rollback.

The direct DID and Jio stages are separate: no carrier setting is needed to prove that Vobiz can receive a call and the Codex agent can speak to its caller.
